# Разбор: 16_redis_cache.py

Redis cache-aside. Небезопасная сериализация, отсутствие TTL и опасный KEYS.

1. **`pickle` для данных из Redis** (строки 16, 19). `pickle.loads` на содержимом кэша —
   если в Redis попадёт подделанное значение (компрометация Redis, инъекция через другую
   ручку, общий инстанс), десериализация выполнит **произвольный код**. `pickle` нельзя
   применять к данным, которым не доверяешь на 100%. Фикс: JSON/msgpack (со схемой), а не pickle.

2. **Нет TTL у закэшированных значений** (строка 19). `r.set(key, ...)` без `ex=`/`px=`.
   Записи живут вечно; при пропущенной инвалидации (баг, гонка, другой путь обновления)
   каталог отдаёт устаревшие данные бесконечно. TTL — страховка от рассинхрона. Нужен `r.set(key, val, ex=TTL)`.

3. **`KEYS` в проде** (строка 30). `r.keys("product:*")` — блокирующая операция, сканирующая
   **всё** пространство ключей; на большой БД она подвешивает Redis для всех клиентов.
   Для массового удаления — `SCAN` (итеративно) или, лучше, версионирование префикса/namespace,
   чтобы инвалидация была O(1).

4. **Гонка инвалидации (cache-aside race)** (строки 12–20 vs 24–25). Классика: поток A
   читает из БД старое значение, поток B обновляет БД и удаляет ключ, поток A кладёт в кэш
   **старое** значение — и оно живёт до следующего апдейта. Смягчается TTL (п.2), а надёжнее —
   инвалидация с задержкой/двойное удаление или запись в кэш только свежего значения под контролем версии.

5. **`if cached:` — falsy-значения ломают кэш** (строка 15). Если в кэше лежит валидное, но
   пустое/falsy значение (например, `pickle` пустого объекта — тут менее вероятно, но с JSON
   `0`/`[]`/`{}` реально), `if cached` даст ложный промах. Отличать «нет ключа» (`cached is None`)
   от «значение пустое».

6. **Негативные ответы не кэшируются, нет анти-«dogpile»** (строки 18–19). Если `db.get_product`
   вернул `None` (нет товара), это не кладётся в кэш — каждый запрос по несуществующему id
   бьёт в БД (cache penetration). Плюс при промахе на горячем ключе все параллельные запросы
   разом идут в БД (dogpile). Стоит кэшировать «отсутствие» с коротким TTL и/или брать лок на прогрев.

7. **Нет обработки недоступности Redis** (все вызовы `r.*`). Если Redis лёг, `r.get`/`r.set`
   кинут — и вместо «промах кэша → идём в БД» вся ручка упадёт. Кэш должен деградировать
   мягко: ошибка Redis → просто идём в БД, а не 500.

8. **Глобальный клиент без таймаутов/пула настроек** (строка 10). `redis.Redis(...)` без
   `socket_timeout`/`socket_connect_timeout` — зависший Redis повесит запрос. И параметры
   подключения (host/port) захардкожены — их место в конфиге.

9. **`update_product`: БД и кэш не согласованы транзакционно** (строки 23–25). Между
   `db.update_product` и `r.delete` окно: если процесс упадёт после апдейта БД до удаления
   ключа, кэш останется со старьём (снова спасает TTL). Порядок «сначала БД, потом инвалидация»
   выбран верно, но стоит осознавать окно и подстраховаться TTL.

10. **Нет аннотаций типов** (все функции). `product_id: int`, `data: dict`, тип результата.

**Итого:** `pickle` из кэша (RCE при недоверенном Redis), отсутствие TTL и `KEYS *` в проде.
Мораль: содержимое кэша — не доверенный источник, TTL обязателен как страховка от рассинхрона,
а `KEYS` в горячем пути — блокировка всего Redis.
