# Разбор: 03_api_client.py

Клиент к платёжному API. Проблемы надёжности и безопасности сетевого кода.

1. **Нет таймаутов** (все три `requests.get/post`). Без `timeout=` запрос может висеть
   бесконечно, если сервер не отвечает, — тред/воркер залипает навсегда. Для платёжного
   клиента это особенно больно. Фикс: `requests.get(url, timeout=(3, 10))`.

2. **HTTP вместо HTTPS** (строка 12). `http://` для платёжного API — ключ и данные
   летят открытым текстом. Плюс токен уходит на незашифрованный канал (см. п.4).

3. **Нет проверки статуса ответа** (`get_payment`, `list_payments`). Сразу `resp.json()`.
   Если пришла 500 с HTML или 404 — `json()` кинет исключение, либо `["items"]` даст
   `KeyError`. Нужен `resp.raise_for_status()` и обработка.

4. **`create_payment` молча возвращает `None`** при не-200 (строки 21–23). Вызывающий
   код думает «платёж создан», получает `None` и падает где-то далеко от причины.
   Ошибку надо поднимать явно.

5. **Авторизация без схемы, а в двух методах вообще забыта** (строки 16, 20, 30–32).
   В `get_payment` заголовок есть, но без схемы: `"Authorization": self.api_key` — обычно
   нужно `f"Bearer {self.api_key}"`, иначе 401. Хуже того — в `create_payment` и
   `list_payments` заголовка авторизации **нет совсем**: эти запросы уйдут анонимными.
   Дублировать headers по методам вручную — источник именно таких пропусков. Фикс: единый
   способ проброса — `requests.Session` с общими `headers` в `__init__` или приватный
   хелпер `_request(...)`, через который идут все вызовы.

6. **Ручная сборка URL и query-параметров** (строки 15, 20, 31–32). Конкатенация строк
   для path/query не экранирует спецсимволы. `payment_id` подставляется в путь как есть —
   надо `params=` и аккуратно формировать путь. `str(user_id)` в URL — потенциальная инъекция в query.

7. **`payments = payments + batch` — аллокации и дубли** (строка 34). Во-первых, `+` в
   цикле копирует список каждый раз, O(n²) по аллокациям; нужен `payments.extend(batch)`.
   Во-вторых, при пагинации через offset/page это ещё и риск **дублей**: если между
   запросами страниц в коллекцию добавились записи, окно сдвинется и одни и те же
   элементы придут дважды. Курсорная пагинация или дедуп по id надёжнее.

8. `if resp.status_code == 200` — часто валидны и 201/204; лучше `raise_for_status`.

9. **Хрупкое условие остановки пагинации** (строка 32). `if batch == []` — во-первых,
   питоничнее `if not batch`. Во-вторых, полагаться на «пустую страницу» как признак
   конца хрупко: в ответе обычно есть явное поле (`total`, `has_next`, `next_cursor`) —
   по нему и надо решать, а не по эмпирике «items закончились».

10. Пагинация без лимита на число страниц — при баге на сервере бесконечный цикл.

11. **`api_key` и `base_url` — публичные атрибуты** (строки 11–12). Внутреннее состояние
    клиента стоит закрыть: `self._api_key`, `self._base_url`. Мелочь по PEP 8, но задаёт
    границу «это не трогать снаружи».

12. **`base_url` захардкожен** (строка 12). Адрес API зашит в код — ни stage/prod
    переключить, ни в тесте на мок направить. Принимать через аргумент конструктора
    (с дефолтом) или из конфига.

13. **Нет аннотаций типов** (все методы и `__init__`). `payment_id: str`, `amount`,
    `currency`, возвращаемые типы — контракт клиента должен читаться из сигнатур.

14. **Тело запроса без схемы** (`create_payment`, строка 20). `data={"amount": ..., "currency": ...}`
    собирается вручную и без валидации: тип amount, допустимые валюты, обязательность полей
    никак не проверяются. Схема (pydantic/dataclass) документирует и валидирует вход. Заодно
    `requests` шлёт `data=` как form-urlencoded — для JSON-API обычно нужен `json=`.

15. **Предположение `page = 1`** (строка 30). Нумерация страниц захардкожена с единицы —
    а API может считать с нуля. Начало пагинации — часть контракта, его стоит свериться
    с доками, а не угадывать.

**Итого:** таймауты, http и обработка ответов. Главный рефлекс ревьюера сетевого кода:
«а где таймаут и где проверка статуса?».
