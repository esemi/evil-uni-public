# Разбор: 03_api_client.py

Клиент к платёжному API. Проблемы надёжности и безопасности сетевого кода.

1. **Нет таймаутов** (все три `requests.get/post`). Без `timeout=` запрос может висеть
   бесконечно, если сервер не отвечает, — тред/воркер залипает навсегда. Для платёжного
   клиента это особенно больно. Фикс: `requests.get(url, timeout=(3, 10))`.

2. **HTTP вместо HTTPS** (строка 12). `http://` для платёжного API — ключ и данные
   летят открытым текстом. Плюс токен уходит на незашифрованный канал (см. п.4).

3. **Нет проверки статуса ответа** (`get_payment`, `list_payments`). Сразу `resp.json()`.
   Если пришла 500 с HTML или 404 — `json()` кинет исключение, либо `["items"]` даст
   `KeyError`. Нужен `resp.raise_for_status()` и обработка.

4. **`create_payment` молча возвращает `None`** при не-200 (строки 21–23). Вызывающий
   код думает «платёж создан», получает `None` и падает где-то далеко от причины.
   Ошибку надо поднимать явно.

5. **Заголовок авторизации без схемы** (строка 16). `"Authorization": self.api_key` —
   обычно нужно `f"Bearer {self.api_key}"`. Как есть — скорее всего 401.

6. **Ручная сборка URL и query-параметров** (строки 15, 20, 31–32). Конкатенация строк
   для path/query не экранирует спецсимволы. `payment_id` подставляется в путь как есть —
   надо `params=` и аккуратно формировать путь. `str(user_id)` в URL — потенциальная инъекция в query.

7. `payments = payments + batch` в цикле — O(n²) по аллокациям; `payments.extend(batch)`.

8. `if resp.status_code == 200` — часто валидны и 201/204; лучше `raise_for_status`.

9. `if batch == []` — питоничнее `if not batch`.

10. Пагинация без лимита на число страниц — при баге на сервере бесконечный цикл.

**Итого:** таймауты, http и обработка ответов. Главный рефлекс ревьюера сетевого кода:
«а где таймаут и где проверка статуса?».
