# Разбор: 20_api_response_parser.py

Клиент к внешнему API. `eval` на ответе, слепое доверие структуре и никакой обработки ошибок.

1. **`eval` на теле ответа** (строка 26). `eval(resp.text)` выполнит **любой код**, пришедший
   от стороннего сервиса (или от MITM, если канал скомпрометирован). Это RCE-дыра, а не парсинг.
   Ответ — JSON, его читают через `resp.json()` / `json.loads`. `eval`/`exec` над внешними
   данными недопустимы никогда.

2. **Слепое доверие структуре ответа** (строки 13–15, 27). `data["main"]["temp"]`,
   `data["weather"][0]["description"]`, `forecast["list"]` — любой промах ключа/пустой список
   уронит парсер с `KeyError`/`IndexError`/`TypeError`. Формат стороннего API мы не
   контролируем; доступ должен быть защищённым (`.get`, проверки) или через валидацию схемой
   (pydantic) с внятной ошибкой.

3. **Нет проверки статуса ответа** (строки 10, 24). Сразу `resp.json()`/`resp.text`. При
   4xx/5xx тело — это ошибка (JSON с другой структурой или HTML), и `data["main"]` упадёт.
   Нужен `resp.raise_for_status()` и обработка не-2xx.

4. **Нет таймаутов** (строки 10, 24). `requests.get` без `timeout=` — зависший сервис держит
   поток бесконечно. Для внешнего API таймаут обязателен.

5. **`resp.json()` может кинуть на не-JSON** (строка 11). Если сервис вернул не-JSON (503-страница,
   пустое тело), `json()` бросит `JSONDecodeError`. Нужна обработка.

6. **Инъекция параметров в URL через конкатенацию** (строки 10, 24–25). `... + city` и
   `... + str(days)` без экранирования: пробелы/спецсимволы в названии города (`"São Paulo"`,
   `"a&b"`) сломают запрос или подменят параметры. Использовать `params={"city": city, "days": days}` —
   `requests` сам корректно закодирует.

7. **«Магическое» вычитание 273.15 без проверки единиц** (строка 17). Предполагается, что
   API отдаёт Кельвины; если формат/версия сменится (Цельсий/Фаренгейт), температура молча
   станет бессмысленной. Хотя бы вынести константу с именем и не хардкодить конверсию вслепую.

8. **`get_many` падает целиком из-за одного города** (строка 30). Dict-comprehension по всем
   городам: первое же исключение в `get_weather` (нет города, таймаут) уронит **весь** батч.
   Для устойчивого пакетного запроса стоит обрабатывать ошибки по городу отдельно (собрать
   успехи, а неудачи — в отдельный список/лог).

9. **`get_forecast` не считает статус/таймаут** — те же проблемы, что 3–5, плюс главный
   `eval` из п.1.

10. **Нет аннотаций типов** (все функции). `city: str`, `days: int`, тип результата.

**Итого:** `eval` над ответом (RCE), слепое доверие структуре и отсутствие проверки статуса/
таймаутов. Мораль: ответ внешнего API — недоверенные данные; парсить его `json()` (никогда
`eval`), проверять статус, обкладывать таймаутом и не доверять, что ключи на месте.
