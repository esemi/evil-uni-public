# Разбор: 14_auth_jwt.py

JWT-аутентификация. Тут дыры, которые полностью обнуляют защиту.

1. **Подпись токена не проверяется** (строка 18). `jwt.decode(..., options={"verify_signature": False})` —
   декодирует **любой** токен без проверки подписи. Кто угодно может собрать
   `{"user_id": 1, "is_admin": true}`, закодировать в JWT — и `verify_token` его примет.
   Это полный обход авторизации. Фикс: `jwt.decode(token, SECRET, algorithms=["HS256"])`.

2. **Секрет захардкожен в коде** (строка 9). `SECRET = "supersecret123"` уедет в git и
   доступен всем, у кого есть исходники — а зная секрет, можно подписывать валидные токены
   с любыми правами. Секрет — только из окружения/секрет-менеджера, и он должен быть длинным/случайным.

3. **`algorithms` не ограничены при декоде** (строка 18, после фикса п.1). Если не задать
   `algorithms=["HS256"]` явно, библиотека может принять токен с `alg: none` или подставным
   алгоритмом (классическая атака на JWT). Всегда фиксируй допустимый список алгоритмов.

4. **Нет проверки срока действия** (`make_token`, строка 13). В payload нет `exp` — токены
   вечные. Украденный токен работает бесконечно, отозвать нельзя. Нужен `exp` (и проверка
   его при декоде — она включена по умолчанию, если поле есть).

5. **`is_admin` внутри токена как источник правды** (строки 13, 34). Права зашиты в токен,
   выданный при логине; отзыв/понижение прав до истечения `exp` невозможны. Критичные
   проверки прав стоит делать по актуальному состоянию в БД, а не слепо доверять claim'у.

6. **Сравнение хэша пароля обычным `==`** (строка 28). `user["password_hash"] == password_hash` —
   не про тайминговую атаку (хэши), но сам подход хранения слаб: **SHA-256 без соли**
   (строка 27) быстро брутится и уязвим к радужным таблицам. Пароли — bcrypt/argon2/scrypt
   с солью; сравнение — через `hmac.compare_digest`/встроенную проверку либы.

7. **`== True` вместо истинностной проверки** (строка 34). `if data["is_admin"] == True:` →
   просто `if data["is_admin"]:`. Питон-антипаттерн; вдобавок `data["is_admin"]` кинет
   `KeyError`, если claim отсутствует.

8. **`verify_token`/`check_admin` не ловят невалидный токен** (строки 18, 33). После фикса
   п.1 `jwt.decode` кидает `InvalidTokenError`/`ExpiredSignatureError` на плохом токене —
   сейчас это уронит хендлер с 500 вместо 401. Нужен `try/except` с корректным ответом.

9. **Нет аннотаций типов** (все функции). `token: str`, `user_id: int`, `is_admin: bool`,
   возвращаемые типы — для auth-кода контракт особенно важен.

10. **`login` возвращает `None` и на «нет юзера», и на «неверный пароль»** — это как раз ок
    (не раскрывать, что именно не так). Но стоит убедиться, что вызывающий не логирует
    разницу и отвечает одинаково, иначе получим user-enumeration.

**Итого:** `verify_signature: False` (полный обход подписи) + захардкоженный секрет +
отсутствие `exp`. Мораль: JWT без проверки подписи и без фиксированного `algorithms` —
это не аутентификация, а её имитация.
