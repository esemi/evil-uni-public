# Разбор: 01_user_registration.py

Ручка регистрации. Тут целый букет, включая дыры безопасности.

1. **SQL-инъекция** (строки 33–36). Запрос собирается через `%`-форматирование с
   пользовательским вводом. `username = "'); DROP TABLE users; --"` — и склад пуст.
   Фикс: параметризованный запрос — `cursor.execute("INSERT ... VALUES (?, ?, ?, ?)", (username, password_hash, email, roles))`.

2. **Мутабельный дефолт + горизонтальная эскалация привилегий** (строка 20, `roles=["user"]`).
   Это тот самый `def f(x=[])`: список создаётся один раз и живёт между запросами.
   Из-за `roles.append("admin")` (строка 26) после первого же запроса с `admin` в имени
   этот список навсегда содержит `"admin"` — и **все последующие пользователи получают роль admin**.
   Фикс: `roles` не должен быть параметром ручки вообще; роль вычисляй внутри из локальной переменной.

3. **Роль admin по подстроке в имени** (строка 25). `"admin" in username` — любой,
   кто назовётся `badmin` или `admin123`, получит админку. Это не проверка прав, это дыра.
   Роли не должны назначаться на основании имени пользователя от клиента.

4. **MD5 для паролей** (строка 28). MD5 быстрый и давно сломан для хранения паролей.
   Нужен bcrypt/argon2/scrypt с солью (`passlib`, `bcrypt`).

5. **Нет обработки отсутствующих полей** (строки 22–23). `data["username"]` кинет
   `KeyError` → 500 вместо 400, если поля нет. И `request.get_json()` вернёт `None`,
   если тело не JSON — тогда `None["username"]` упадёт с `TypeError`.

6. **Соединение с БД не закрывается и нет транзакционности** (строки 30–37).
   `db = get_db()`, но нет `close()` и нет `try/finally`/контекстного менеджера —
   утечка коннектов. Курсор тоже не закрывается. А если `execute`/`commit` кинет
   исключение — коннект останется висеть в открытой транзакции. Нужен `with`-контекст
   (`sqlite3.connect` умеет быть менеджером транзакции) или `try/except` с явным
   `rollback` и закрытием в `finally`.

7. **`debug=True` в проде** (строка 44). Werkzeug-debugger позволяет выполнять
   произвольный код через браузер. Никогда не должно уехать в прод.

8. Пароль в открытом виде мог бы утечь в логи — стоит быть аккуратнее с тем, что логируется.

9. Нет валидации формата email / длины пароля.

10. `email` может быть `None`, но пишется в БД без учёта nullable-схемы.

11. **`get_db` — внутренний хелпер, а имя публичное** (строка 14). Функция не часть
    внешнего API модуля; по PEP 8 такое стоит называть `_get_db`, чтобы отделить от
    публичной поверхности. Мелочь, но помогает читателю понять границы модуля.

12. **Нет аннотаций типов** (`register`, `get_db`). Сигнатуры без типов — на ревью
    сложнее понять контракт, а mypy/IDE не подстрахуют. `roles` вдобавок ещё и лишний
    параметр (см. п.2), но и остальным аргументам/возврату типы бы не помешали.

13. **Возврат — голый dict, статусы строками** (строка 39). `jsonify({"status": "ok", ...})`:
    ответ не описан схемой (pydantic/marshmallow/dataclass), а `"ok"` — магическая строка.
    Схема ответа + константа/enum для статуса ловят опечатки и документируют контракт ручки.

**Итого:** ключевое, что здесь надо поймать, — SQL-инъекция и мутабельный дефолт,
протекающий между запросами.
