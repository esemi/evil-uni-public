# Разбор: 18_batch_import.py

Батч-импорт в БД. Инъекция, коммит на каждой строке и частичный успех без отката.

1. **SQL-инъекция** (строки 15–16, 26, 28–30). Все запросы собираются через `%`-форматирование
   с данными из внешнего источника. `row["name"] = "'); DROP TABLE users; --"` — и таблицы
   нет. Для батча из недоверенного источника это особенно опасно. Фикс: параметризация —
   `cur.execute("INSERT ... VALUES (%s, %s)", (row["email"], row["name"]))` (psycopg2 сам экранирует).

2. **`commit` на каждой строке** (строки 18, 32). На десятках тысяч записей — десятки тысяч
   отдельных транзакций: медленно (fsync на каждую) и создаёт нагрузку на БД. Батчить нужно:
   один коммит на пачку (или на N строк), а ещё лучше — `execute_values`/`COPY` для массовой вставки.

3. **Частичный успех без отката** (весь `import_users`). Если импорт упадёт на 5000-й строке,
   первые 4999 уже закоммичены, а остальные нет — БД в полу-импортированном состоянии, и
   повторный запуск наплодит дублей (см. п.5). Нужна транзакция на весь батч с откатом при
   ошибке — либо идемпотентный upsert, чтобы повтор был безопасен.

4. **Курсор создаётся в цикле и не закрывается** (строки 14, 25). `cur = conn.cursor()` на
   каждой итерации, `close()` нет — курсоры копятся до конца функции. Курсор стоит открывать
   через `with conn.cursor() as cur:` (и обычно одного достаточно на весь батч).

5. **Нет обработки конфликтов/дублей** (строка 15). Обычный `INSERT` упадёт на дубле email
   (если есть unique-констрейнт) и оборвёт весь импорт. Нужен `ON CONFLICT DO NOTHING/UPDATE`
   (upsert) — это же делает повторный запуск безопасным (п.3).

6. **`company` может быть `None`** (строки 27–30). `fetchone()` вернёт `None`, если компании
   нет → `company[0]` кинет `TypeError`. Нужна проверка «нашли ли компанию» и решение, что
   делать со строкой (пропустить/ошибка/создать).

7. **N+1 в `import_with_lookup`** (строки 25–27). Для каждой строки — отдельный `SELECT`
   компании. На больших пачках это тысячи лишних round-trip'ов. Лучше подтянуть маппинг
   `name -> id` одним запросом заранее или сделать `INSERT ... SELECT` с join.

8. **Глобальное соединение на модуле** (строка 8). Один `conn` на весь процесс, не
   потокобезопасен, после ошибки остаётся в aborted-транзакции до `rollback`. Соединение
   лучше открывать на запуск задачи и закрывать в `finally`.

9. **Строка подключения захардкожена** (строка 8). Параметры БД в коде — их место в
   конфиге/окружении.

10. **Нет обработки ошибок и логирования прогресса** — при падении нет ни лога, где споткнулись,
    ни счётчика обработанного; для кронового батча это важно для диагностики и докрутки.

11. **Нет аннотаций типов** (обе функции). `rows: list[dict]`, возвращаемый тип.

12. **`imported` считается безусловно** (строки 17–19). `imported += 1` после каждого `execute`,
    независимо от того, реально ли вставилась строка. С upsert-ом `ON CONFLICT DO NOTHING` (п.5)
    дубликат **не вставится**, а счётчик всё равно вырастет — статистика импорта врёт. Считать
    надо по фактическому результату (`cur.rowcount`), и заранее решить, что для отчёта значит
    «импортировано»: новые записи или все обработанные.

**Итого:** SQL-инъекция, коммит на каждой строке и частичный успех без отката/идемпотентности.
Мораль: батч в БД — это транзакция и параметризованные запросы; коммит в цикле и «упали
на середине без отката» превращают повторный прогон в источник дублей.
