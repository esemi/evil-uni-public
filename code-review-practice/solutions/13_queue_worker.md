# Разбор: 13_queue_worker.py

Воркер очереди. Главное — потеря сообщений из-за раннего ack и проглоченных ошибок.

1. **`ack` до обработки — потеря сообщений** (строки 22, 25). `basic_ack` вызывается
   **раньше** `process_message`. Если воркер упадёт (или процесс убьют) между ack и концом
   обработки, брокер уже считает сообщение доставленным — задача **потеряна навсегда**.
   Ack надо слать **после** успешной обработки; при ошибке — `nack`/`reject` (с requeue или
   в dead-letter).

2. **Проглоченные исключения** (строки 27–29). `except Exception: pass` — любая ошибка в
   обработке молча теряется: ни лога, ни ретрая, ни dead-letter. Сообщение при этом уже
   заакано (п.1), результат в БД не записан — тихая потеря данных. Нужно логировать и
   осознанно решать судьбу сообщения (retry/DLQ).

3. **Нет idempotency** (`process_message`). При корректном «ack после обработки» возможна
   двойная доставка (воркер обработал, но упал до ack — брокер передоставит). `save_to_db`
   должен быть идемпотентным (upsert по `task["id"]`), иначе получим дубли результатов.

4. **Busy-loop через `basic_get` + `sleep`** (строки 18–21). Поллинг очереди с
   `time.sleep(0.1)` — костыль: лишние round-trip'ы к брокеру и задержка до 100 мс на пустой
   очереди. Идиоматичнее push-модель — `basic_consume` с колбэком, брокер сам будит воркер.

5. **Нет prefetch / QoS** — при переходе на `basic_consume` без `basic_qos(prefetch_count=N)`
   брокер зальёт воркер всеми сообщениями сразу. Ограничение prefetch держит нагрузку под контролем.

6. **`json.loads` без обработки битого тела** (строка 11). Кривое/не-JSON сообщение кинет
   `JSONDecodeError`; сейчас его проглотит `except` из п.2, но по-хорошему такое сообщение —
   кандидат в dead-letter, а не в бесконечный requeue (иначе «отравленное» сообщение
   заблокирует очередь).

7. **Слепой доступ к ключам** (строки 12–13). `task["payload"]`, `task["id"]` — нет ключа →
   `KeyError`. Стоит валидировать структуру сообщения (схема/pydantic).

8. **Нет backoff при ошибках брокера** — если `basic_get` начнёт кидать (брокер недоступен),
   цикл будет молотить вхолостую. Нужен reconnect с экспоненциальным backoff.

9. **Нет graceful shutdown** (строка 17, `while True`). Воркер нельзя корректно остановить:
   по SIGTERM он оборвётся посреди обработки. Нужен флаг остановки/обработка сигналов, чтобы
   доработать текущее сообщение и выйти.

10. **Нет аннотаций типов** (все функции). `body: bytes`, `task_id`, `result` — контракт
    обработчика неясен.

11. **Нет логирования** (весь воркер). Демон в проде без логов — чёрный ящик: не видно, что
    получено, что обработано, где упало (см. проглоченный `except` в п.2). Нужен `logging` с
    уровнями по всему циклу: получили сообщение (debug), обработали (info), ошибка (error).

12. **Внутренние функции с публичными именами** (`process_message`, `do_heavy_work`,
    `save_to_db`). Это не внешний API модуля — по PEP 8 стоит `_process_message` и т.д.,
    чтобы обозначить границу.

13. **`save_to_db` пишет `result` без схемы** (строки 13, 33). `do_heavy_work` возвращает
    произвольный dict, который как есть уходит в БД — структура нигде не зафиксирована и не
    валидируется. Результат стоит описать схемой (dataclass/pydantic), тогда и запись, и
    чтение имеют контракт.

**Итого:** ack до обработки + `except: pass` = тихая потеря задач при любом сбое. Мораль:
в воркере очереди порядок «обработал → записал → подтвердил» священен, а идемпотентность —
плата за at-least-once доставку.
