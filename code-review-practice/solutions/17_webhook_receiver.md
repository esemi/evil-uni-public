# Разбор: 17_webhook_receiver.py

Приёмник вебхуков в интернете. Нет проверки подписи, SSRF и тяжёлая работа в хендлере.

1. **Подпись вебхука не проверяется** (весь хендлер). Ручка публичная — кто угодно может
   слать `POST /webhook` с любым `order_id`/`status` и менять заказы. Платёжные провайдеры
   подписывают тело (HMAC-заголовок); нужно проверять подпись до любой обработки, иначе это
   открытый эндпоинт управления заказами. Это дыра №1.

2. **SSRF через `callback_url` из payload** (строки 21–22). `requests.get(callback_url)` идёт
   на URL, пришедший **от клиента**. Атакующий подставит `http://169.254.169.254/...`
   (метадата облака), `http://localhost:6379` (внутренние сервисы) — сервер сходит туда от
   своего имени. Нельзя ходить по произвольным URL из внешнего ввода: белый список хостов,
   запрет приватных диапазонов, а лучше — не брать URL из payload вообще.

3. **Тяжёлая обработка синхронно в хендлере** (строки 24, 34). `process_heavy_analytics`
   выполняется прямо в запросе — провайдер ждёт ответа, ловит таймаут и **ретраит вебхук**,
   плодя дубли. Вебхук должен быстро принять (201/200) и уйти, а тяжёлую работу делать в
   фоне (очередь/задача).

4. **Нет idempotency** (`update_order`). Провайдеры доставляют вебхуки at-least-once (и
   ретраят при таймауте из п.3). Без ключа идемпотентности (id события) один и тот же
   статус применится многократно. Обработку надо дедуплицировать по event-id.

5. **Слепой доступ к ключам** (строки 15–16, 21). `data["order_id"]`, `data["status"]`,
   `data["callback_url"]` — нет ключа → `KeyError` → 500. `request.get_json()` вернёт `None`,
   если тело не JSON → `None["order_id"]` упадёт с `TypeError`. Нужна валидация схемой и 400 на кривой вход.

6. **Нет таймаута у исходящего запроса** (строка 22). `requests.get(callback_url)` без
   `timeout=` — зависший колбэк держит воркер, а с учётом п.3 ещё и весь хендлер.

7. **Нет проверки статуса/ошибок колбэка** (строка 22). Результат `requests.get` игнорируется:
   упал колбэк или нет — неизвестно, ретраев/логов нет.

8. **`status` из payload без валидации значения и без контроля переходов** (строки 16, 19).
   Во-первых, в `update_order` уедет любой произвольный статус от клиента — допустимые статусы
   должны быть фиксированным набором (enum), всё остальное отклонять. Во-вторых, у заказа
   обычно есть **машина состояний**: не всякий переход валиден (из `paid` нельзя откатиться в
   `pending`, из `refunded` — никуда). Проверять надо не только «статус из списка», но и
   «допустим ли переход из текущего состояния в новый» — иначе вебхук (или атакующий, п.1)
   переведёт заказ в некорректное состояние.

9. **Нет ограничения размера тела** — публичная ручка принимает JSON любого размера; большой
   payload — вектор DoS. Стоит лимитировать размер запроса.

10. **Нет аннотаций типов** (все функции). `order_id`, `status: str`, `data: dict`.

11. **Ответ ручки без схемы** (строка 26). `jsonify({"ok": True})` — контракт ответа нигде не
    описан. Как и на входе (п.5), выход стоит описать схемой (pydantic/marshmallow), а не
    собирать голый dict руками — тогда формат ответа документирован и проверяем.

**Итого:** отсутствие проверки подписи (открытое управление заказами), SSRF по `callback_url`
и синхронная тяжёлая обработка, провоцирующая ретраи-дубли. Мораль: публичный вебхук — это
недоверенный ввод; проверяй подпись, не ходи по URL из тела и отвечай быстро, вынося работу в фон.
