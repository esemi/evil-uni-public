# Разбор: 10_inventory.py

Учёт склада. Баг типов + частичное списание заказа + краевые случаи.

1. **`process_order` конкатенирует строку с числом** (строка 39). `"...: " + inventory.total_value()`
   — `total_value()` возвращает число (int/float), `str + float` → `TypeError`, функция
   всегда падает в конце. Фикс: `+ str(inventory.total_value())` или f-строка.

2. **Частичное списание заказа без атомарности** (строки 36–38). `process_order` идёт по
   позициям и вызывает `remove_stock`, **игнорируя возвращаемый `bool`**. Если по одной
   позиции остатка не хватило (`remove_stock` вернул False), первые позиции уже списаны,
   а эта — нет. Заказ «processed», но склад в неконсистентном состоянии, и клиент получит
   не весь заказ. Нужно либо сначала проверить наличие всего, потом списывать, либо откатывать.

3. **`KeyError` на неизвестном товаре** (`add_stock`, `remove_stock`, строки 12, 15).
   `self.items[name]` кинет `KeyError`, если товара нет в словаре. Для `add_stock` нового
   товара это точно баг (нельзя завести позицию). Нужна проверка наличия ключа.

4. **`remove_stock` возвращает `bool`, но никто его не проверяет** — контракт есть, а
   пользоваться им забыли (см. п.2). Молчаливо-игнорируемый результат — красный флаг.

5. `total_value` на `float`-ценах — для денег корректнее `Decimal`.

6. Нет валидации `qty >= 0` — можно «добавить» отрицательное количество и увести остаток в минус.

7. `low_stock` и `total_value` итерируют `self.items` вручную — читается нормально, но
   `total_value` можно выразить через `sum(... for ...)`.

8. Конструктор принимает внешний `items` и хранит по ссылке — внешний код может мутировать
   склад мимо методов класса.

**Итого:** `TypeError` в `process_order` (падает всегда) + неатомарное частичное списание
+ игнор возвращаемого `bool`. Мораль: если метод возвращает флаг успеха, вызывающий обязан его проверять.
